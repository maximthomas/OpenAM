# OpenAM REST response volatility — what a capture tool must normalise

Survey for task 2.15's re-record CI job. Answers one question: **what changes between two identical
calls to an unchanged instance**, and can a capture tool normalise it away well enough to make a
re-record byte-identical.

**Verdict: byte-for-byte determinism is achievable** with the 16 normalisation rules below, plus
one capture-order constraint that is not a normalisation rule. Measured across two bringups rather
than inferred. See [Determinism](#determinism-verdict).

Rules 1–14 are this survey's. **Rules 15 and 16 were added later, by task 2.15**, when building the
CI job showed that a value this document had classified correctly had been acted on wrongly — see
[Build stamp](#build-stamp-2--added-by-task-215-not-by-this-survey).

## What was probed, and how

Instance both times: OpenAM **16.2.0-SNAPSHOT**, revision `8628aba262`, built
`2026-August-08 09:56`, at `http://openam.example.org:8080/openam`. Containers `openam-idp`
(`openam-e2e:local`) and `opendj-idp`.

**Bringup 1 — the full survey.**

- All **41 in-scope rows** of [REQUESTS.md](REQUESTS.md), expanded to **49 concrete calls** (some
  rows cover two statuses — the `404` probes and the `401` anonymous path — and both were issued).
- **Two full passes, 8 seconds apart**, curl only, every response body and header set written to a
  separate file and compared with `cmp`/`diff`/a JSON-aware differ. No body was read whole.
- Every observed status matched REQUESTS.md's `Status` column, including the anonymous `401` on
  `POST /json/users?_action=idFromSession` and the `201`s on create.
- Listing-order stability got a **6-consecutive-call** probe rather than a 2-run diff, because a
  two-run diff cannot distinguish "stable" from "intermittently reordered".
- Result: **11 of 49 bodies and 49 of 49 header sets differed** between the two passes.
- 48 candidate host/instance-bound values were recorded verbatim as a baseline for bringup 2.

**Bringup 2 — after `openam-reset.sh` destroyed and rebuilt the containers and re-ran the
configurator.**

- All **48 baseline values re-observed** by the same paths and partitioned STABLE / PER-BRINGUP.
  This is what separates "looks host-specific" from "measured to regenerate".
- A **9-request subset** re-run twice, chosen to cover all five volatility categories plus both
  ends of the schema-reordering case, and to include three controls that must *not* move:

  | Request | Covers |
  |---|---|
  | `POST /json/realms/root/authenticate` (admin) | tokens, `Set-Cookie`, `Date` |
  | `POST /json/realms/root/authenticate` (callbacks leg) | the `authId` nonce, `AMAuthCookie`, `Content-Length` |
  | `POST /json/sessions?_action=getSessionInfo` | the three session timestamps + `sessionHandle` |
  | `GET /json/realms/root/realm-config/authentication` | `ETag` moving on a byte-identical body |
  | `POST /json/global-config/authentication?_action=schema` | key reordering, largest payload (20 KB) |
  | `POST /json/global-config/services/rest?_action=schema` | key reordering, smallest payload |
  | `GET /json/serverinfo/*` | **control** — must be byte-identical |
  | `GET /json/realms/root/users/demo` | `createTimestamp`; **control** for `objectClass` ordering |
  | `GET /json/global-config/realms?_queryFilter=true` | **control** — listing ordering |

  The controls are the point: a subset that only samples known-volatile endpoints cannot detect a
  rule that has started over-normalising.

## Volatile catalogue — 16 distinct fields

Grouped as the brief asks. "Rule" is the proposed normalisation, and is the tool's specification.

### Timestamps (6)

| # | JSON path / header | Where | Observed | Rule |
|---|---|---|---|---|
| 1 | `Date` header | **all 49 responses** | RFC-1123, changes every call | **Drop.** |
| 2 | `$.latestAccessTime` | `POST /json/sessions?_action=getSessionInfo` | `2026-08-12T02:40:41Z` → `…02:40:51Z` | Replace with `<TS>`. |
| 3 | `$.maxIdleExpirationTime` | same | `03:10:41Z` → `03:10:51Z` | Replace with `<TS>`. |
| 4 | `$.maxSessionExpirationTime` | same | `04:40:40Z` → `04:40:50Z` | Replace with `<TS>`. |
| 5 | `$.modifyTimestamp[*]` | `GET`/`PUT /json/realms/root/users/demo` | `20260812024042Z` → `…024052Z` | Replace each element with `<TS>`. |
| 6 | `$.createTimestamp[*]` | `GET /json/realms/root/users/{demo,amadmin}` | `20260812023736Z` → `20260812025309Z` **across bringups** | Replace each element with `<TS>`. |

**`createTimestamp` is the one field a two-run diff cannot see, and it is the only value in the
whole 48-value baseline that the second bringup changed.** It is fixed for the life of a container
and regenerated by every reconfigure. A tool that normalised only what a two-run diff surfaces
would pass its own tests and then fail the first real re-record. This is precisely the trap the
survey existed to catch, and it is the sole member of the PER-BRINGUP partition.

Rule 5 (`modifyTimestamp`) normalises the *value* when the key is present. Whether the key is
present at all is a separate matter — a state dependency, not volatility. See
[Ordering dependencies](#ordering-dependencies-between-requests); do not conflate the two.

### Tokens and session identifiers (4)

| # | JSON path / header | Where | Rule |
|---|---|---|---|
| 7 | `$.tokenId` | `POST /json/authenticate`, `POST /json/realms/root/authenticate` | Replace with `<TOKEN>`. 102 chars, fresh per call. |
| 8 | `Set-Cookie: iPlanetDirectoryPro=…` | the same two | Replace the **value only**; keep `path`, `domain`, `SameSite`. |
| 9 | `Set-Cookie: AMAuthCookie=…` | the callbacks step of both authenticate shapes | Replace the value only. **Length also varies** (106 vs 110 chars). |
| 10 | `$.sessionHandle` | `POST /json/sessions?_action=getSessionInfo` | Replace with `<SESSION-HANDLE>`. Form `shandle:AQIC…`. |

The token's internal structure decodes to `SI=01`, `SK=<random>`, `S1=`. Only `SK` is per-session;
`SI` is the **server id** and belongs to the host-specific list below.

The `AMAuthCookie=LOGOUT; Expires=Thu, 01 Jan 1970 00:00:10 GMT` header on a *successful* login is
a constant and needs no rule.

### Nonces (1)

| # | JSON path | Where | Rule |
|---|---|---|---|
| 11 | `$.authId` | first leg of both authenticate shapes | Replace with `<AUTHID>`. |

A JWT whose **length varies between calls** — 353 and 359 chars observed across 6 pulls. This is
the direct cause of finding 13. It is also a one-shot credential; see
[Unsafe to repeat](#unsafe-to-issue-twice).

### Server-generated identifiers and hashes (2)

| # | Header | Where | Rule |
|---|---|---|---|
| 12 | `ETag` | every SMS config `GET`/`PUT`, and `GET users/demo` | **Drop.** |
| 13 | `Content-Length` | responses carrying a variable-length token | **Drop**, or recompute after normalisation. |

**`ETag` is the subtle one.** It changes between calls *even when the response body is
byte-identical*:

| Endpoint | body | run 1 | run 2 |
|---|---|---|---|
| `GET /json/realms/root/realm-config/authentication` | identical | `"1368330367"` | `"208223034"` |
| `GET /json/global-config/services/rest` | identical | `"1107071409"` | `"1607442409"` |
| `GET .../realm-config/services/baseurl` | identical | `"1957455358"` | `"1475581659"` |

So it is not a content hash in any usable sense — it reads as a Java `hashCode()` over a map with
non-deterministic iteration order. **A tool that derives or validates `ETag` from the body will be
wrong.** `GET /json/serverinfo/*` is the lone exception (`"-546398656"` both runs); it is recorded
as a real baseline candidate rather than a volatile field.

`Content-Length` differed only on `POST /json/authenticate` (696 → 702), tracking the `authId`
length. It is stable elsewhere, but must be dropped generally because normalisation changes body
length anyway.

### Build stamp (2) — added by task 2.15, not by this survey

| # | JSON path | Where | Rule |
|---|---|---|---|
| 15 | `$.date` | `GET /json/serverinfo/version` | Replace with `<BUILD-DATE>`. |
| 16 | `$.revision` | `GET /json/serverinfo/version` | Replace with `<REVISION>`. |

**These two are corrections to this document, and the correction is worth reading before trusting
the partition below.** The survey measured both values and put them in [STABLE](#stable-44--normalise-for-portability-not-for-re-record)
as "build-bound, not bringup-bound", which is accurate and was the wrong conclusion to draw from.
Task 2.3 pinned them on it deliberately, expecting a rebuild to be an occasional event that deserved
a human look.

Task 2.15's drift job builds the war it then records against, on every run. So:

| Field | Source | Moves when |
|---|---|---|
| `date` | Ant `<tstamp>`, `yyyy-MMMM-dd HH:mm` — `openam-server/openam-server-prepare-war.xml:36`, filtered in as `@DATESTAMP@` | **every `mvn install`**, to the minute |
| `revision` | `buildnumber-maven-plugin`'s `git.short.sha1` — `pom.xml:1812`, filtered in as `@REVISION@` | every commit |
| `version` | the POM version | a version bump |

`date` alone makes a byte diff against a committed capture fail on **100 % of runs**, and it fails in
a way no re-record can fix: re-recording stamps the recording machine's own build minute, and the
next scheduled run stamps a new one. A value the job itself regenerates is not a drift signal.

So 15 and 16 are rule 6's kind of rule — measured to move only across bringups, invisible to a
two-run diff on one instance, and fatal to a re-record. `version` stays pinned: it is the field that
actually says the AM under test is a different AM, and it moves only when someone bumps it.

### JSON key ordering (1) — the largest finding

| # | JSON path | Where | Rule |
|---|---|---|---|
| 14 | every `properties` object, at **any** nesting depth | **all five `_action=schema` responses** | **Sort object keys recursively.** |

Six consecutive calls to `POST /json/global-config/authentication?_action=schema` produced **six
distinct byte sequences** — reordering on every call, not intermittently. Yet all six were
**deep-equal**, and a recursive key sort collapsed all six to **one** output.

The reordering is confined to `properties` objects and their key *set* is always identical:

| Response | objects reordered / total | key sets equal |
|---|---|---|
| `global-config/authentication` schema (20 KB) | 8 of 71 | yes, all |
| `realm-config/authentication` schema (17 KB) | 5 of 61 | yes, all |
| realm-scoped `realm-config/authentication` schema | 7 of 61 | yes, all |
| `global-config/services/rest` schema | 1 of 6 | yes |
| `services/baseurl` schema | 1 of 7 | yes |

Sorting is **safe** here: each property carries an explicit integer `propertyOrder` (identical
across runs) that carries display order, so the XUI does not depend on key order. Note that not
every object carries `propertyOrder` — container nodes such as `defaults` lack it — so
**sort lexicographically by key; do not try to sort by `propertyOrder`.**

Sorting all object keys everywhere (not just under `properties`) is equivalent and simpler, since
JSON objects are unordered by definition. That is what the tested normaliser does.

### Array ordering in listings — settled: no rule needed

Six consecutive calls each to `global-config/realms?_queryFilter=true`,
`realm-config/services?_queryFilter=true`, `_action=getAllTypes` and
`_action=getCreatableTypes&forUI=true`, plus `GET users/demo` (for the 18-element `objectClass`
array), produced **one distinct byte output each** within a bringup.

**Across the rebuild, every one of those orderings came back identical** — including the two that
would have caught a reordering if one existed: `getCreatableTypes`' 19 entries in their
non-alphabetical order (`dashboard,globalization,session,user,passwordreset,…`) and `objectClass`'
18 LDAP values. A fresh configurator reproduces them exactly.

**So listings need no sort rule, and must not be given one.** This was the named condition that
would have flipped the verdict to structural-only; it was tested directly and it did not flip.
Sorting listings would have discarded real ordering signal from the API for no benefit.

## Host- and instance-specific values — measured across two bringups

These are stable between two runs of one instance, so they are **invisible to a two-run diff** —
the trap the brief names. 48 candidates were recorded on bringup 1 and re-observed by the same
paths on bringup 2, after `openam-reset.sh` destroyed the containers and re-ran the configurator.

**The partition, which is the point of the exercise:**

| | count | meaning |
|---|---|---|
| **STABLE across bringups** | **44** | reproduced exactly by a fresh configurator. Normalise only for cross-*machine* portability |
| **PER-BRINGUP** | **1** | regenerated by every reconfigure. Must be normalised even on this same box |
| per-call volatile | 2 | the two `ETag` probes — already rule 12, never baseline constants |
| state-dependent presence | 1 | `modifyTimestamp` — an ordering constraint, not a value |

**The single PER-BRINGUP value is `$.createTimestamp[*]`** on every user
(`20260812023736Z` → `20260812025309Z`). Rule 6 already covers it.

That is a much better result than the setup implied. `openam-up.sh` runs the AM container with
`--rm` and **no data volume**, and always re-runs the configurator (`openam-reset.sh` is just
down+up), so there is no persisted instance and every identifier *could* have regenerated. In
practice the configurator is deterministic: it reproduced even the `serverinfo/*` `_rev` config
hash (`-546398656`) bit-for-bit across a full rebuild.

### STABLE (44) — normalise for portability, not for re-record

| Value | Observed | Note |
|---|---|---|
| Base URL | `http://openam.example.org:8080/openam` | also appears inside `global-config/servers` |
| Hostname / port / deployment URI | `openam.example.org` / `8080` / `/openam` | container hostname is also `openam.example.org` |
| **Server id** | `01` | **survived the rebuild in all three places** — `servers[0]._id`, the `amlbcookie` value, and the `SI` segment inside every session token. So session tokens carry no per-bringup fragment; only the `SK` segment is per-session random |
| **Site id** | *none configured* | `global-config/sites` was empty on both bringups. If a later bringup configures one, it becomes a new target |
| AM version / revision / build date | `16.2.0-SNAPSHOT` / `8628aba262` / `2026-August-08 09:56` | build-bound, not bringup-bound. **Stable only for a fixed war.** `revision` and `date` are now rules 16 and 15 — the drift job rebuilds, so "stable across bringups" was never the question to ask of them. `version` alone stays pinned |
| **Realm DNS aliases** | `["openam","openam.example.org"]` | root realm `aliases`; same values, same order both times |
| Cookie domain | `example.org` | `serverinfo/*` `$.domains[0]`, and the `domain=` attribute of every `Set-Cookie` |
| `serverinfo/*` `_rev` / `ETag` | `-546398656` | identical across the rebuild — the strongest single evidence that the configurator is deterministic |
| Config-store LDAP suffix | `dc=openam,dc=openidentityplatform,dc=org` | in `universalid` for **every** user, and in `getSessionInfo.universalId` |
| User-store LDAP suffix | `dc=example,dc=com` | in `demo`'s `dn` — a *different* suffix from `universalid` |
| `successUrl` | `/openam/console` | embeds the deployment URI |
| Realm ids | base64url of the realm path (`Lw` = `/`) | derived, not random — portable if the realm path is |
| Listing orderings | see [array ordering](#array-ordering-in-listings--settled-no-rule-needed) | all reproduced exactly |

There is no instance/deployment UUID in any in-scope response; the server id plays that role.

### PER-BRINGUP (1) — must be normalised even for a re-record on this machine

| Value | Bringup 1 | Bringup 2 | Rule |
|---|---|---|---|
| `$.createTimestamp[*]` on every user | `20260812023736Z` | `20260812025309Z` | rule 6 — replace with `<TS>` |

### Flagged but not measurable

`AM_ENC_KEY` is empty in `openam-up.sh`, so AM generates `am.encryption.pwd` at configure time.
It is **not observable over the REST surface**, so it could not be partitioned. It changes every
encrypted value at rest. No in-scope response was seen to expose an encrypted value, so it is
recorded as a known unknown rather than a normalisation target.

## Authentication

**Admin session.** `POST /json/realms/root/authenticate` with `Accept-API-Version:
protocol=1.0,resource=2.1` and headers `X-OpenAM-Username: amadmin` / `X-OpenAM-Password:
ampassword`. Returns `$.tokenId` in one call — no callback exchange needed. Pass it on subsequent
requests as the **`iPlanetDirectoryPro` request header**, which is what the Playwright fixtures do
(REQUESTS.md Fact 6); the cookie jar works too but the header is simpler for a capture tool.

**A non-admin session is also required.** Two in-scope rows need it:

- `POST /json/sessions?_action=logout` — REQUESTS.md marks it "yes — end user". Logging out the
  *admin* session here would invalidate the tool's own credential mid-capture.
- `GET`/`PUT /json/realms/root/users/demo` are reachable with either, but the `@local-server` specs
  drive them as `demo`.

Use `demo` / `changeit` by the same call shape.

**Ending the session.** `POST /json/sessions?_action=logout` with the token in the
`iPlanetDirectoryPro` header — returns `{"result":"Successfully logged out"}`. The tool **must**
log out every session it opens: each authenticate leaves a live server-side session that otherwise
lingers for the 30-minute idle timeout, and a capture run creates several. Log out the admin
session **last**.

Two authenticate calls in the scope carry `X-NoSession: true` and create **no** session, so they
need no teardown.

## Unsafe to issue twice

Three, and the first is the one that will actually bite.

1. **`POST /json/realms/root/authenticate` — second leg (filled callbacks). One-shot.**
   Replaying a captured step-2 request with its recorded `authId` returns
   **`408 Request Time-out` / `"Session has timed out"`**, not `200`. The `authId` is consumed by
   the first submission. A capture tool **cannot** replay a recorded login; it must re-run the
   callback exchange from step 1 each time, and a fixture that replays step 2 verbatim will fail.
2. **`POST /json/sessions?_action=logout` — one-shot.** `200` first, **`401 Unauthorized`** on
   replay with the same token. Any request using that token afterwards is also `401`.
3. **State-mutating rows**, safe only as a create→delete cycle within one pass:
   `POST global-config/realms?_action=create`, `PUT`/`DELETE global-config/realms/<id>`,
   `PUT realm-config/authentication`, `POST/PUT/DELETE realm-config/services/baseurl`
   (both path shapes), and `PUT /json/realms/root/users/demo`. Issued twice without a teardown in
   between, `_action=create` returns a conflict rather than the recorded `201`. This survey drove
   each as a full create→…→delete cycle per pass, which is what made them comparable.

## Ordering dependencies between requests

Yes — four, all of which constrain capture order.

1. **The authenticate exchange is stateful.** Step 2 is only valid against the `authId` step 1
   returned (REQUESTS.md Fact 4). Server-side state links them.
2. **`PUT /json/realms/root/users/demo` permanently changes the shape of every later
   `GET /json/realms/root/users/demo`.** This is the one diff normalisation could **not** remove:
   the run-1 response has no `modifyTimestamp` key at all; the run-2 response has one, because
   pass 1's `PUT` created it. A **field appearing**, not a value changing. So the first capture
   against a fresh instance genuinely differs in shape from every later one — the tool must either
   run the `PUT` before the `GET` in a fixed order, or capture `GET users/demo` only after a
   warm-up write.

   **The rebuild confirmed this directly.** On the fresh instance, before any `PUT`, `demo` has no
   `modifyTimestamp` key at all. It is created by the first write and never removed thereafter.

   **Keep this separate from the volatile catalogue.** It is a constraint on capture *order*, not a
   field to normalise. Rule 5 normalises `modifyTimestamp`'s value once the key exists; nothing
   should normalise its presence. A rule that dropped the key outright would also hide a genuine
   regression in the profile-write path — the one place this endpoint's behaviour actually matters.
3. **Realm-scoped requests require the realm to exist**, created by
   `POST global-config/realms?_action=create` earlier in the same capture.
4. **The `404`/`200` pairs on `…/services/baseurl` are order-dependent by construction** — the
   `404` row is a "does it exist yet" probe that only returns `404` before the create.

Sessions are otherwise independent: no in-scope response varied with what preceded it in the same
session, beyond the above.

One further shape dependency, unrelated to ordering: **`GET /json/serverinfo/*` returns `_id` and
`_rev` only when no `Accept-API-Version` header is sent.** With `resource=1.1` *or* `resource=1.0`
both keys are absent. Presence depends on version negotiation, not on session or state, so the tool
must record the header it sent alongside the response.

## Determinism verdict

**Byte-for-byte determinism is achievable.** The 16 rules above are sufficient, and task 2.15's CI
job can assert byte equality rather than structural equality with a tolerance.

That verdict survives rules 15 and 16 unchanged — the survey's own measurements were right, and what
those two rules correct is a decision taken on top of them rather than a finding. But note what it
took to expose: the gap was not visible to any comparison this survey ran, because every one of them
held the war fixed. **A precondition of byte equality is that something in the comparison varies the
way CI varies it.** Preconditions 1–5 below are the same statement in the small.

The rules were tested, not assumed, at three levels:

| Test | Result |
|---|---|
| All 49 request pairs, two passes against one container | **48 / 49 identical** after normalisation; 49/49 header sets identical |
| 9-request subset incl. 3 controls, two passes on the rebuilt instance | **9 / 9 identical**, bodies and headers |
| 48 host/instance-bound values, across a full destroy-and-reconfigure | **44 stable, 1 per-bringup** — and that one is already rule 6 |

The single residual in the first row is **not volatility**: it is the `modifyTimestamp` key
appearing after pass 1's `PUT`, dependency 2 above. It does not arise under a fixed request order
from a known starting state, and no rule should paper over it.

**Both conditions that would have forced a "no" were tested directly, and neither fired:**

- **Array ordering in listings survived the rebuild** — `getCreatableTypes`' 19 non-alphabetical
  entries and `objectClass`' 18 LDAP values came back in exactly their previous order. No sort rule
  is needed, and adding one would destroy real API signal.
- **Server id `01` survived in all three of its appearances**, including inside the session token.
  Had it moved, every token would carry a per-bringup fragment and normalising the token value
  alone would not have been enough.

### What the CI job must do for this to hold

Byte equality is achievable **given the rules plus these preconditions** — they are part of the
specification, not caveats bolted on:

1. Apply all 16 rules, including rule 6 (`createTimestamp`) and rules 15–16 (the build stamp).
   Those three are the ones a within-bringup test cannot justify and a re-record cannot survive
   without: 6 needs a second bringup to show itself, 15 and 16 need a second *build*.
2. **Sort object keys recursively; do not sort arrays.** The asymmetry is load-bearing.
3. **Never derive or validate `ETag` from the body** — it moves between calls on byte-identical
   bodies. Drop it.
4. Capture in a **fixed request order from a freshly configured instance**, so the
   `modifyTimestamp` state dependency lands the same way each time.
5. Re-run the authenticate callback exchange per capture; never replay a recorded `authId`.

### Residual risk, stated honestly

The cross-bringup comparison was made at the level of the **48-value identifier baseline plus the
9-request subset**, not a full 49-pair byte-diff across bringups — the bringup-1 response dumps
were deleted as scratch before the rebuild, on instruction. The baseline was chosen to cover every
value judged instance-bound, and the subset re-confirmed all five volatility categories on fresh
config, so the exposure is a field that is both outside the baseline and outside the subset. Given
that the configurator reproduced even the `serverinfo/*` `_rev` hash exactly, that exposure is
small — but it is not zero, and the cheap way to close it is to keep the first CI re-record's diff
output on failure rather than only its exit code.

**Closed by measurement, 2026-08-14, while building task 2.15's job.** The full-tree cross-bringup
diff this paragraph called for has now been run, and the exposure it describes is not there:

| Comparison | Result |
|---|---|
| Full 48-call tree, re-recorded after `openam-reset.sh` (destroys both containers, re-runs the configurator), against the committed capture | **47 of 48 payloads byte-identical.** The 49th file, `serverinfo/version`, differed only in the two fields rules 15 and 16 now normalise |
| Two consecutive re-records, same instance, no reset between | **49 of 49 byte-identical** |

So no field outside the 48-value baseline and the 9-request subset moved across a reconfigure. The
recommendation to keep the diff output rather than only the exit code stands anyway — it costs
nothing and it is what makes a red run readable — but it is no longer covering an open risk.

`am.encryption.pwd` remains unobservable over REST. No in-scope response exposes an encrypted
value, so it does not affect this verdict; it would if the surface ever grew to include one.

## Instance state

**Bringup 1** ended with one disclosed residue: `demo` carried a `modifyTimestamp`
(`20260812024052Z`) it had not had before, because the survey drove the in-scope
`PUT /json/realms/root/users/demo` as a value-preserving round-trip — `givenName`, `sn`, `cn` and
`mail` were byte-identical to their previous values, but LDAP stamped a modify time regardless. It
could not be removed. It went with the container on reset, as predicted.

**Bringup 2 is clean.** This pass was read-only apart from authentication:

- No realm, service or user was created or modified. `demo` still has **no** `modifyTimestamp`,
  which is both the expected state and the confirmation of the state-dependency finding.
- Every session opened was explicitly logged out, admin last, each verified
  `200 Successfully logged out`.
- The instance was left **up**, not torn down.

The scratch identifier baselines (`.identifiers-run{1,2}.json`) were deleted once their content was
folded into the [host-specific partition](#host--and-instance-specific-values--measured-across-two-bringups)
above; that section is now the record.

## Not determined

- `am.encryption.pwd` is not observable over the REST surface; recorded as a known per-bringup
  secret rather than measured. It does not affect the verdict, because no in-scope response exposes
  an encrypted value.
- The cross-bringup evidence is the 48-value baseline plus the 9-request subset, not a full 49-pair
  byte-diff across bringups. See [residual risk](#residual-risk-stated-honestly).
